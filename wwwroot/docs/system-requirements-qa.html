Contractor Attendance & Health Declaration Monitoring

A web-based system that records contractor attendance through ID-card scanning at a kiosk, applies a self-administered health and waiver gate at entry, and provides administrators with management, correction, and audit tools.

System version2.9.2.0
Document date17 August 2026
AudienceQA team — functional & regression test design
PlatformASP.NET Core 8 MVC · MySQL (stored procedures via Dapper) · SignalR · LDAP
Test basisManual UI testing on the deployed build; no automated suite exists
SECTION 01

System overview

Contractors scan their ID card at an unattended kiosk. Each scan is either a TIME IN (starts an attendance session) or a TIME OUT (closes the open session). On TIME IN the contractor completes a short self-declaration — health status and waiver consent — within a configurable window. Combinations that mean "not allowed to enter" automatically close the session. Administrators manage reference data (providers, projects, contractors), correct attendance records, and every admin change is audit-logged.

User roles

RoleAuthenticationCapabilities
ContractorNone — kiosk is publicScan ID; declare health status & waiver consent within the window
Public viewerNoneView attendance dashboard (real-time); view, filter and export history logs
AdminLDAP login + membership of configured AD group; 30-minute sessionManage providers, projects, contractors (incl. bulk import), system configuration; edit/delete timelogs; view audit logs

Status vocabulary used throughout

  • Health status: FIT or UNFIT — stored as a MySQL ENUM on the attendance record.
  • Waiver consent: UNDERSTOOD or NOT_UNDERSTOOD.
  • "Not allowed to enter" combination = UNFIT or FIT + NOT_UNDERSTOOD. Both auto-set a TIME OUT and block same-day re-entry.
MODULE K

Kiosk scan processing

Route / (also /Home/Index). Left panel: scan input and contractor identity. Right panel: health declaration after TIME IN. All scan business rules execute server-side in order — see Scan rule sequence for the exact evaluation order.

FR-K-01

Scan input and submission

The kiosk accepts an employee ID typed or emitted by a keyboard-wedge barcode scanner into a single field. Pressing Enter submits the scan; the field has autofocus and is cleared and refocused after every attempt.

Acceptance criteria
  • Empty input submits nothing (no request, no error dialog).
  • Successful and failed scans both clear the input and restore focus for the next contractor.
  • When ScanInputReadOnly is enabled in system configuration, the field is read-only — keyboard typing is rejected, scanner input still works (see FR-S-02).
FR-K-02

Unknown ID is rejected

A scanned ID with no matching contractor record is rejected. No attendance record is created.

Acceptance criteria
  • Inline error shows exactly Contractor not found and auto-clears.
  • Contractor info panel is hidden; no time_logs row is written.
FR-K-03

Inactive contractor is rejected

A contractor whose active flag is 0 cannot TIME IN or TIME OUT.

Acceptance criteria
  • Inline error shows Contractor is inactive.
  • No attendance record is created or modified.
FR-K-04

Duplicate-scan debounce

A scan arriving within DebounceThresholdSeconds of the contractor's most recent scan event is rejected. The "most recent scan event" is the session's time_out when it exists, otherwise its time_in. The check applies to both TIME IN and TIME OUT attempts.

Acceptance criteria
  • Rejection message is exactly Duplicate scan - wait N seconds. where N is the configured threshold.
  • The comparison is strict: at exactly N seconds elapsed the scan is processed (boundary test).
  • Deactivating/reactivating the threshold in System Config changes behaviour on the next scan without redeployment.
FR-K-05

TIME OUT closes the open session

If the contractor has an open session (TIME IN recorded, no TIME OUT), the scan records time_out = now on that record. The contractor's own ID is stamped as updated_by (self-service).

Acceptance criteria
  • Success message is exactly SUCCESS TIME OUT, shown with distinct (non-green) styling.
  • The health declaration panel does not appear for a TIME OUT scan.
  • TIME OUT is never blocked by an inactive project/provider or by an earlier blocked health combination — those rules only gate TIME IN.
  • A subsequent scan after the debounce window starts a fresh TIME IN (new record).
FR-K-06

Same-day re-entry block

If the contractor's latest TIME IN today already carries a "not allowed to enter" combination, further scans that day are blocked (both re-TIME IN attempts and TIME OUTs of the auto-closed record are rejected by this rule before session logic runs).

Acceptance criteria
  • UNFIT block message: Not Allowed to Enter. You are UNFIT.
  • Waiver block message: Not Allowed to Enter. You did not understand waiver.
  • After an admin corrects the record (FR-T-02) to an allowed combination, the contractor can scan in again the same day.
FR-K-07

TIME IN blocked when project is inactive

TIME IN requires the contractor's assigned project to exist and be active. This check runs after the open-session check so that deactivating a project mid-day never traps an on-site contractor.

Acceptance criteria
  • Message: Not Allowed to Enter. Project is In-Active.
  • A contractor with no project assigned is also blocked by this rule (project not found).
  • A contractor already timed-in can still TIME OUT after the project is deactivated.
FR-K-08

TIME IN blocked when provider is inactive

Same gate as FR-K-07, applied to the contractor's provider.

Acceptance criteria
  • Message: Not Allowed to Enter. Provider is In-Active.
  • Mid-day provider deactivation still allows open sessions to TIME OUT.
FR-K-09

TIME IN creation and defaults

When all gates pass, the system creates a time_logs row with time_in = now, time_out = NULL, health_status = FIT, waiver_consent = UNDERSTOOD — both declaration values are safe defaults the contractor may change within the window.

Acceptance criteria
  • Success message is exactly SUCCESS TIME IN (green styling).
  • Left panel displays the contractor's name, provider (code + name), project (code + name), position and assigned area.
  • Defaults are visible pre-selected in the health declaration panel (FR-K-10).
FR-K-10

Health declaration panel lifecycle

After a TIME IN, the right panel shows the declaration form with a visible countdown. The form hides when the countdown reaches zero or immediately when any next scan is submitted — whichever comes first.

Acceptance criteria
  • Countdown starts at the configured HealthDeclarationWindowSeconds and is displayed to the user.
  • On expiry or next scan the panel is replaced by the empty-state message and all timers are cleared.
  • A TIME OUT scan never shows the declaration panel.
MODULE H

Health declaration & waiver consent

The declaration has two independent controls: health status (FIT / UNFIT) and waiver consent (UNDERSTOOD / NOT_UNDERSTOOD), each pre-selected to the safe default. A configurable list of sickness items is also presented on the panel. Any change is submitted immediately on selection.

FR-H-01

Declaration form controls

Radio groups for health status and waiver consent, both defaulting to the allowed combination; sickness items are rendered from the Health_Declaration_Sickness configuration (see FR-S-05).

Acceptance criteria
  • On panel open, FIT and UNDERSTOOD are selected.
  • Selecting any radio immediately persists the change — there is no separate submit step.
  • Sickness items shown match the configured list; when configuration is missing, the built-in default list (Fever, Cough, Cold, Body Pain, Headache, Sore Throat, Fatigue, Nausea, Diarrhea) is used.
FR-H-02

Change window enforced server-side

Declaration updates are accepted only while now − time_in < HealthDeclarationWindowSeconds. The UI countdown mirrors the same value, but the server re-validates on every update.

Acceptance criteria
  • Update submitted after expiry fails with exactly Health declaration and waiver consent window has expired. Changes allowed only within N seconds of TIME IN.
  • No database change occurs on a rejected update.
  • Boundary: an update at exactly N seconds after TIME IN is rejected (strict less-than).
FR-H-03

UNFIT sets automatic TIME OUT

Selecting UNFIT persists the status and stamps time_out = now, closing the session immediately.

Acceptance criteria
  • Kiosk shows a large critical alert titled Not Allowed with text You are not allowed to enter company premises due to health status.
  • Record persists health_status=UNFIT with time_out populated.
  • Same-day re-scans are blocked per FR-K-06.
FR-H-04

FIT + NOT_UNDERSTOOD also blocks entry

A contractor who declares FIT but NOT_UNDERSTOOD waiver consent is treated as not allowed to enter: the update persists and time_out = now is set.

Acceptance criteria
  • Selecting NOT_UNDERSTOOD shows the critical alert You are marked as FIT but do not understand the waiver.
  • Record persists waiver_consent=NOT_UNDERSTOOD with time_out populated.
  • Same-day re-scan blocked with the waiver message from FR-K-06.
FR-H-05

Reversal within the window

Returning to the allowed combination (FIT + UNDERSTOOD) inside the window clears the auto-set time_out back to NULL, reopening the session.

Acceptance criteria
  • After UNFIT → FIT + UNDERSTOOD (within window): time_out is NULL, session open, success alert reads ALLOWED TO ENTER / FIT and understand the waiver.
  • Reversal attempts after window expiry fail with the FR-H-02 message; the TIME OUT stays.
  • Only auto-generated TIME OUTs are reversible in this flow — a TIME OUT recorded by a physical scan is not undone by the declaration.
FR-H-06

Enum validation

Update requests must carry valid enum values: health status ∈ {FIT, UNFIT}, waiver consent ∈ {UNDERSTOOD, NOT_UNDERSTOOD}.

Acceptance criteria
  • Invalid values (API-level tests) return a validation failure and write nothing.
  • Waiver consent omitted from the request defaults to UNDERSTOOD client-side.
FR-H-07

Locked after the window

Once the declaration window expires, health status and waiver consent are locked at the kiosk. Only an admin correction (FR-T-02) can change them.

Acceptance criteria
  • Kiosk panel is hidden after expiry; no control can re-open it for that record.
  • Admin TimeLogs edit can still change both fields at any time.
FR-H-08

Alerts on the kiosk

Declaration outcomes surface as full-width popups that auto-dismiss, after which focus returns to the scan field.

Acceptance criteria
  • Allowed: ALLOWED TO ENTER — FIT and understand the waiver.
  • Unfit: NOT ALLOWED TO ENTER — You are UNFIT.
  • Waiver not understood: NOT ALLOWED TO ENTER — You do not understand the waiver.
  • Focus returns to the scan input after every alert closes.
MODULE D

Attendance dashboard

Route /Attendance — a public, real-time view of today's attendance for monitoring staff. Updates arrive by push; no manual refresh is required.

FR-D-01

Real-time updates via SignalR

The page opens a WebSocket connection to the /attendanceHub hub and refreshes the table whenever attendance changes are broadcast.

Acceptance criteria
  • A scan at the kiosk is reflected on an open dashboard within seconds, without refresh.
  • If the hub connection fails, the page shows a Connection Error alert stating real-time updates are unavailable, and the initially loaded table remains visible.
FR-D-02

Table columns and privacy masking

Columns: Employee ID, Name, Provider, Time In, Time Out, Health Status, Actions. Employee IDs are masked — rendered as one dot per character.

Acceptance criteria
  • Employee ID column shows dots equal in count to the ID length; the raw ID never appears.
  • Times render in local time format; empty Time Out renders an Active badge.
FR-D-03

Health status badges

Acceptance criteria
  • FIT renders as a green badge; UNFIT as a red badge.
FR-D-04

Table behaviour

Acceptance criteria
  • Default sort: Time In descending; page length 25.
  • With no records today, the table shows the empty-state message No attendance records for today.
FR-D-05

Public access

Acceptance criteria
  • No login is required to view the dashboard.
FR-D-06

Row actions

Active rows expose a Time Out action so monitoring staff can close a session without the badge; UNFIT rows expose a waiver-related action inherited from an older workflow.

Acceptance criteria
  • Time Out appears only on rows with no time_out and a FIT status; using it records the time out.
  • See "Known legacy items" (Section 17) for the Approve Waiver button — there is no waiver-approval workflow in the current system; treat it as out of scope and do not design positive tests for it.
MODULE R

History logs & export

Route /Home/HistoryLogs — public, read-only attendance history with filtering and client-side Excel export.

FR-R-01

Public read-only listing

Acceptance criteria
  • Page loads without authentication.
  • No edit or delete affordance exists anywhere on the page; it is display-only.
FR-R-02

Filters

Attendance can be filtered by employee ID, date range (from/to), and health status.

Acceptance criteria
  • Filtering by date range returns only records whose relevant timestamps fall inside the range.
  • Health status filter returns only FIT or only UNFIT rows as selected.
  • Combined filters intersect (AND logic).
FR-R-03

Table behaviour

Acceptance criteria
  • Default ordering: Time In, most recent first.
  • Column sorting, free-text search and pagination operate on the loaded result set.
FR-R-04

Excel export respects filters

Export generates the workbook client-side (SheetJS) from the currently filtered data.

Acceptance criteria
  • The export button is visible only when the table has data; with an empty result set it is hidden.
  • Exported rows match the active filters exactly — no unfiltered rows leak into the file.
  • Export of 1000+ records completes without error.
FR-R-05

Health status display

Acceptance criteria
  • UNFIT rows are visually distinguished (red treatment) from FIT rows in the history table.
MODULE A

Authentication & session

Admin access uses corporate LDAP credentials plus AD group membership, held in a server-side session. The kiosk, dashboard and history pages never require authentication.

FR-A-01

LDAP login

Login at /Auth/Login authenticates username and password against the corporate directory through the LDAP API service.

Acceptance criteria
  • Valid credentials succeed and redirect to /Admin.
  • Invalid credentials fail with an error message and no session is created.
FR-A-02

Admin AD group requirement

The authenticated user's group memberships must contain the group named in the AdminADGroup configuration key.

Acceptance criteria
  • Authenticated user without the group is denied admin access (access-denied response).
  • Changing AdminADGroup in System Config changes which group grants access, without redeployment.
FR-A-03

Session establishment and timeout

On success the session stores the admin's employee number, display name and Role=Admin. Idle timeout is 30 minutes.

Acceptance criteria
  • After 30 minutes of inactivity, the next admin request redirects to the login page.
  • Active use keeps the session alive (sliding expiration behaviour per request).
FR-A-04

Protected route enforcement

All /Admin/* pages require an admin session.

Acceptance criteria
  • Unauthenticated navigation to any admin page redirects to /Auth/Login (with return URL) rather than rendering admin content.
  • Direct API calls to admin JSON endpoints without a session do not return data.
FR-A-05

Logout

Acceptance criteria
  • Logout clears the session and returns the user to the kiosk home page.
  • After logout, admin pages are no longer reachable without re-login.
FR-A-06

Display of identity

Acceptance criteria
  • The admin interface shows the logged-in admin's display name, and audit entries record the admin's employee number.
MODULE P

Provider & project management

Admin route /Admin/Projects. Providers are created and managed inside the Projects workflow — there is no standalone Providers page. Core entities use soft delete (Active/Inactive) only; they are never hard-deleted.

FR-P-01

Provider creation with auto-generated code

Creating a provider captures name, address, PIC and contact number. The provider code is generated automatically from the provider name as an acronym (e.g. Alpha Circuits Inc → ACI), with deterministic fallbacks (consonant extraction, then timestamp-based) when a clean acronym can't be formed.

Acceptance criteria
  • The code field is not manually entered; it is derived from the name.
  • Two providers whose names yield the same acronym do not collide — fallback keeps codes unique.
  • New provider is active by default and immediately usable for projects.
FR-P-02

Project code generation

Project codes are generated by the database in the format {ProviderCode}-{YY}-{NNN} — e.g. ACI-26-005 — sequentially within each provider, resetting to 001 at each new year. Generation is transaction-safe (rollback on failure).

Acceptance criteria
  • The Nth project created for a provider in a year receives that provider's next sequential number for that year.
  • The first project of a new calendar year for a provider receives 001.
  • Simultaneous project creation attempts never produce duplicate codes (transaction protection).
FR-P-03

Project creation and validation

A project belongs to exactly one provider and carries a project name and contract start/end dates.

Acceptance criteria
  • Project cannot be created without a valid parent provider.
  • Contract dates are required; contract end must not precede contract start.
FR-P-04

Project listing and status filter

Acceptance criteria
  • Projects table lists all projects with their provider; an Active/Inactive status filter narrows the list.
  • Projects by provider can be retrieved for cascading dropdowns elsewhere in the admin UI.
FR-P-05

Project update

Acceptance criteria
  • Editable fields (name, dates, provider assignment) persist correctly.
  • Updates are audit-logged (FR-L-03).
FR-P-06

Soft delete (set inactive)

Acceptance criteria
  • Setting a project or provider inactive is a status change only — the record and its history remain.
  • Deactivation immediately blocks new TIME INs for its contractors (FR-K-07/08) while allowing open sessions to TIME OUT.
  • No hard-delete action exists for providers or projects.
FR-P-07

Contractors-per-project view and export

From the projects screen, admins can open a contractor list for a selected project, and export that list to Excel.

Acceptance criteria
  • The modal lists only contractors assigned to the selected project.
  • Excel export from the modal downloads the listed contractors.
FR-P-08

Provider search

Acceptance criteria
  • Provider dropdowns/lists support server-side search by name/code, used by the contractor and project forms.
MODULE C

Contractor management

Admin route /Admin/Contractors. Contractors are enrolled by admins; there is no self-registration and no approval workflow — an enrolled contractor can scan immediately.

FR-C-01

Contractor listing, filters and reset

Acceptance criteria
  • Table lists contractors with their provider and project.
  • Filters: project filter and Active/Inactive status filter; a Reset filters control restores the unfiltered list.
  • Export to Excel downloads the contractors respecting active filters.
FR-C-02

Contractor creation with field validation

Required identity includes employee ID, name, gender, birthdate, provider and project; the project must belong to the chosen provider. Contact number is optional; address is captured.

Acceptance criteria
  • Missing employee ID or contractor data is rejected with a clear message; nothing is saved.
  • Unknown provider → Provider not found; unknown project → Project not found.
  • Project belonging to a different provider → The selected project does not belong to the selected provider.
  • A contractor may be enrolled with no project initially (project assigned later).
FR-C-03

Duplicate enrollment guard

The same person (name matched case-insensitively + identical birthdate) cannot be enrolled twice into the same project — including rows committed earlier in the same bulk batch.

Acceptance criteria
  • Duplicate via the create form → A contractor with this name and birthdate is already enrolled in this project.
  • Name matching ignores case and surrounding whitespace.
  • The same person may exist under a different project (contractors change projects by being issued a new employee ID).
FR-C-04

Contractor update and reactivation

Acceptance criteria
  • Edit modal opens with current values, including the contractor's current project.
  • An inactive contractor can be edited back to active (reactivation) and can then scan again.
  • Updates are audit-logged (FR-L-03).
FR-C-05

Contractor soft delete

Acceptance criteria
  • Setting a contractor inactive immediately blocks their scans (FR-K-03) but preserves their attendance history.
  • No hard-delete action exists for contractors.
FR-C-06

Bulk enrollment via Excel

Admins upload an Excel file of contractors against a chosen provider and project. The upload carries the provider code, project code, file name and parsed rows.

Acceptance criteria
  • Empty payload → No contractor rows were provided for import.
  • Missing provider/project → Provider and Project are required.
  • Project must exist and belong to the provider; otherwise the import is rejected with the corresponding message.
  • Duplicates within the uploaded batch (name + birthdate, same project) are rejected by the same guard as FR-C-03 once earlier rows are committed.
  • Valid rows are committed; the result distinguishes succeeded and failed rows so partial success is visible.
FR-C-07

Excel export

Acceptance criteria
  • Export downloads an .xlsx of the contractor list currently matching the filters.
FR-C-08

Contractor detail fields

Acceptance criteria
  • Captured fields include employee ID, name, gender, birthdate, contact number (optional), address, position, area of destination, provider and project.
  • These details surface at the kiosk on scan (name, provider, project, position, area — FR-K-09).
MODULE T

TimeLogs management (admin correction)

Admin route /Admin/TimeLogs. The correction tool for attendance records — edit fields, delete records, export, with full audit trail.

FR-T-01

Timelogs listing

Acceptance criteria
  • Table lists attendance records with employee name and waiver consent shown alongside the record fields.
  • Filters (employee, date range, health status) narrow the list; Export to Excel respects the active filters.
FR-T-02

Edit timelog

Admins can edit time_in, time_out, health_status and waiver_consent on any record, at any time — including declarations long past the kiosk window.

Acceptance criteria
  • Edited values persist and are reflected immediately in history/dashboard views.
  • Saving a "not allowed to enter" combination with a blank time_out auto-fills time_out = time_in (zero-duration session) rather than leaving it open.
  • Correcting a blocked record to an allowed combination re-enables same-day entry at the kiosk (FR-K-06).
  • Every edit stamps updated_by (admin employee number) and updated_at.
FR-T-03

Delete timelog

Unlike core entities, timelogs can be hard-deleted for data cleanup.

Acceptance criteria
  • Deletion requires an explicit confirmation dialog.
  • On confirm the record is permanently removed; success message Timelog deleted successfully.
  • Deletion is captured in the audit log (FR-L-03).
FR-T-04

Audit trail fields on records

Acceptance criteria
  • Records corrected by admin expose who (updated_by) and when (updated_at).
  • Self-service TIME OUTs stamp the contractor's own ID as updated_by (FR-K-05).
FR-T-05

Export to Excel

Acceptance criteria
  • Export produces an .xlsx of the filtered timelog set, including health status and waiver consent columns.
FR-T-06

Admin-only access

Acceptance criteria
  • All TimeLogs management actions require an admin session (FR-A-04).
MODULE S

System configuration

Admin route /Admin/SystemConfig. Business-rule parameters live in the system_config table and apply at runtime — changes take effect without redeployment or restart.

FR-S-01

View and edit configuration

Acceptance criteria
  • All configuration keys are listed with current values and descriptions.
  • Editing a value persists it; the next request that reads the key uses the new value.
  • Configuration changes are audit-logged (FR-L-03).
FR-S-02

ScanInputReadOnly toggle

Rendered as a toggle switch. When enabled, the kiosk scan input is read-only so stray keyboard input can't corrupt scanned IDs (scanner-detection script works with this).

Acceptance criteria
  • Toggling on then loading the kiosk makes the field read-only; scanner wedge input still registers.
  • Toggling off restores manual typing.
FR-S-03

Time windows are in seconds

Both windows are configured in seconds (historically minutes — converted in v2.5.0.0). Code fallback default is 120 seconds when the key is missing or invalid.

Acceptance criteria
  • Setting HealthDeclarationWindowSeconds=60 makes the kiosk countdown start at 60 and the server reject updates after 60s.
  • Missing or non-numeric key falls back to 120 seconds (kiosk still usable — verify no crash).
FR-S-04

AdminADGroup runtime change

Acceptance criteria
  • Changing the group name changes which users can log in as admin on the next login attempt, without restart.
MODULE L

Audit logging

Admin route /Admin/AuditLogs. Administered changes are captured before/after with the acting user.

FR-L-01

Audited scope

Audit entries are written for provider, project, contractor (including bulk enrollment), system configuration, and timelog changes (edit and delete).

Acceptance criteria
  • Each of the above admin operations produces an audit entry in the same request.
  • Kiosk self-service scans are not admin audit events (their trail is updated_by/updated_at on the record).
FR-L-02

Captured detail

Each entry stores entity type, action, reference ID, before-values (data_from) and after-values (data_to) as readable indented snake_case JSON, the acting user, and a timestamp.

Acceptance criteria
  • before/after JSON keys use snake_case and remain human-readable when opened directly.
  • When no acting user is available the entry is attributed to System.
FR-L-03

Changes-only diff rendering

The audit log view renders each entry's detail as a diff table showing only the fields that changed.

Acceptance criteria
  • Unchanged fields do not appear in the diff view.
  • Old and new values are shown side by side for each changed field.
FR-L-04

Audit never blocks the operation

A failure while writing the audit entry must not fail the business operation that triggered it.

Acceptance criteria
  • The admin operation reports success even if the audit write fails (failure is logged server-side, surfaced in the Response message).
FR-L-05

Audit log listing

Acceptance criteria
  • Admins can browse audit entries; newest activity is reachable; the view requires admin session.
SECTION 12

Scan processing rule sequence

The server evaluates every scan in this fixed order; the first failing rule wins. This table is the primary reference for kiosk test design.

StepRulePass outcomeFail outcome / exact message
1Contractor existsContinueContractor not found
2Contractor is activeContinueContractor is inactive
3Debounce: now − last scan event (time_out else time_in) ≥ thresholdContinueDuplicate scan - wait N seconds.
4Today's latest TIME IN is an allowed combination (not UNFIT, not FIT+NOT_UNDERSTOOD)ContinueNot Allowed to Enter. You are UNFIT. or Not Allowed to Enter. You did not understand waiver.
5Open session check — session open?Yes → TIME OUT: set time_out = now, SUCCESS TIME OUT. Done.No open session → continue to 6
6Project exists and is activeContinueNot Allowed to Enter. Project is In-Active.
7Provider exists and is activeContinueNot Allowed to Enter. Provider is In-Active.
8Create TIME INtime_in = now, FIT, UNDERSTOOD, time_out NULL → SUCCESS TIME IN; declaration panel opens—
Order matters

Steps 6–7 (project/provider gates) deliberately sit after the open-session check at step 5. That ordering is itself a requirement: a contractor already on-site can always TIME OUT even if their project or provider was deactivated mid-day. Regression-test it.

SECTION 14

Non-functional requirements

NFR-01

Platform & data access

ASP.NET Core 8 MVC; all database access exclusively through MySQL stored procedures via Dapper (no ad-hoc SQL in code). Stored procedures return result sets only — no OUT parameters.

NFR-02

Graceful error handling

Every service operation returns a structured success/message payload; database or unexpected errors surface as user-safe messages ("Database error…", "Error processing scan") with detail logged server-side — never raw exceptions to the kiosk.

NFR-03

Real-time delivery

Dashboard updates arrive over WebSocket (SignalR) within seconds of a scan; the page must remain usable (initial data + explicit connection error) when the hub is unreachable.

NFR-04

Session security

Admin sessions: HTTP-only cookie, 30-minute idle timeout, enforced server-side on every admin request.

NFR-05

Export performance

Excel exports are generated client-side and must handle 1000+ filtered records without error or page freeze.

NFR-06

Code generation concurrency

Year-based project code generation is transaction-protected; concurrent creations must never issue duplicate codes (rolling rollback on failure).

NFR-07

Runtime configurability

Business-rule changes via System Config take effect on the next request — no redeployment or app restart.

NFR-08

Browser support

Evergreen desktop browsers (Edge/Chrome). The kiosk is the primary target device, including keyboard-wedge barcode scanners.

SECTION 16

Edge cases recommended for test design

  • Debounce boundary — scan again at exactly N seconds after the last event (allowed) vs. N−1 s (rejected). Both clock edges: after a TIME IN and after a TIME OUT.
  • Declaration window boundary — toggle to UNFIT at exactly the window limit; strict less-than means it should be rejected.
  • Full reversal chain — TIME IN → UNFIT (auto TIME OUT) → FIT+UNDERSTOOD within window (TIME OUT cleared) → scan again after debounce (should TIME OUT, not create a new session).
  • Waiver-only block — FIT + NOT_UNDERSTOOD blocks entry exactly like UNFIT, including same-day re-scan message wording.
  • Mid-day deactivation — deactivate project/provider while a session is open: TIME OUT must still succeed; a new TIME IN must be blocked.
  • Blocked-then-corrected — UNFIT morning record, admin corrects to FIT+UNDERSTOOD, contractor scans in again same day — must succeed.
  • Next-scan takeover — contractor B scans while contractor A's declaration panel is open: A's panel and timer are cleared; B's flow is unaffected.
  • Year rollover — first project for a provider in a new year receives -01-001-style numbering; codes from the previous year are untouched.
  • Acronym collision — two providers whose names yield the same acronym; codes must remain unique.
  • Bulk import mixed validity — an upload containing valid rows and duplicate rows (both vs. existing data and within the batch); verify partial-success reporting.
  • Empty/missing config — delete or corrupt window/threshold keys; kiosk must fall back to 120 s rather than fail.
  • Session expiry mid-task — let an admin session idle past 30 minutes, then submit an admin action; expect login redirect, not a silent failure.
  • Unknown / inactive / projectless contractor scans — cover all three rejection messages distinctly.
  • Export fidelity — apply each filter (and combinations) in History, TimeLogs and Contractors, then export; file contents must match the visible rows exactly, including the empty-result case (button hidden).
SECTION 17

Out of scope & known legacy items

Explicitly out of scope

  • Safety officers / waiver approval workflow — removed. Health gatekeeping is self-administered only; no third party approves entry.
  • Detailed health questionnaire — no symptom checkboxes or medication fields are persisted; the declaration is FIT/UNFIT + waiver consent.
  • Contractor self-service — contractors have no accounts, logins or personal dashboards; they interact only through the kiosk.
  • Hard deletes of providers, projects and contractors — these entities are Active/Inactive only.
  • Automated test suite — none exists; all QA is manual against the deployed build.

Known legacy items

Approve Waiver button on the dashboard

The attendance dashboard's Actions column still renders an Approve Waiver button on UNFIT rows, inherited from the removed waiver workflow; no backend approval endpoint exists. Do not build positive tests for it. If it misbehaves in your build, file it as a defect against the legacy cleanup (removal) rather than the waiver feature.
